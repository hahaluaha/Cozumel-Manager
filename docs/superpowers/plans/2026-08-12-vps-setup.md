# Hostinger VPS Setup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Provision, harden, and stand up a WordPress-ready VPS for `cozumelhomes.net`, verified over HTTP without touching live DNS.

**Architecture:** SSH key auth → non-root `deploy` sudo user → root/password SSH disabled → UFW + fail2ban → WordOps-managed nginx/PHP-FPM/MariaDB stack → WordPress site created and verified via `/etc/hosts` override. No DNS cutover in this plan.

**Tech Stack:** Ubuntu 24.04 LTS, OpenSSH, UFW, fail2ban, WordOps (nginx + PHP-FPM + MariaDB + WP-CLI + Let's Encrypt), WordPress.

## Global Constraints

- Server: Ubuntu 24.04 LTS, IP `2.25.104.105`, root password already set by Fernando.
- Domain: `cozumelhomes.net` (GoDaddy DNS) — currently points at a parking page, not live traffic. Do not touch GoDaddy DNS in this plan.
- SSH key file: `~/.ssh/id_ed25519_cozumel_vps` (private) / `~/.ssh/id_ed25519_cozumel_vps.pub` (public), comment `cozumel-vps-deploy`. One shared key for Fernando and Claude — do not generate a second key.
- Sudo user: `deploy`. Root SSH login must end up disabled — never re-enable it after Task 4.
- Kelley's access (wp-admin) is untouched by this plan — no task should modify WordPress user accounts.
- Out of scope: migrating local site content, unattended-upgrades, DNS cutover, Let's Encrypt SSL (needs live DNS, not yet available).

### Task 1: Generate the SSH keypair and add it to root

**Files:** none (local `~/.ssh/`, remote `/root/.ssh/authorized_keys`)

**Interfaces:**
- Produces: `~/.ssh/id_ed25519_cozumel_vps` / `.pub`, used by every later task's `ssh`/`scp` calls.

- [ ] **Step 1: Generate the keypair**

```bash
ssh-keygen -t ed25519 -C cozumel-vps-deploy -f ~/.ssh/id_ed25519_cozumel_vps -N ""
```

- [ ] **Step 2: Verify the key files exist with correct permissions**

```bash
ls -l ~/.ssh/id_ed25519_cozumel_vps ~/.ssh/id_ed25519_cozumel_vps.pub
```
Expected: private key mode `600` (`-rw-------`), public key mode `644`.

- [ ] **Step 3: Copy the public key to root@2.25.104.105**

This is the one step that still needs the root password (typed interactively — do not put it in a command):

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_cozumel_vps.pub root@2.25.104.105
```

- [ ] **Step 4: Verify key-based root login works**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps root@2.25.104.105 "echo KEY_LOGIN_OK"
```
Expected: prints `KEY_LOGIN_OK` with no password prompt.

- [ ] **Step 5: Commit the plan checkpoint (no repo changes yet — skip git commit, this task only touches the VPS and local `~/.ssh/`)**

No commit needed — nothing in the git repo changed.

### Task 2: Create the `deploy` sudo user

**Files:** none (remote server state only)

**Interfaces:**
- Consumes: `~/.ssh/id_ed25519_cozumel_vps.pub` from Task 1.
- Produces: `deploy` user with passwordless key login and sudo access, used by every task from here on instead of root.

- [ ] **Step 1: Create the user and add to sudo group**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps root@2.25.104.105 "adduser --disabled-password --gecos '' deploy && usermod -aG sudo deploy"
```

- [ ] **Step 2: Install the public key for `deploy`**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps root@2.25.104.105 "mkdir -p /home/deploy/.ssh && cp /root/.ssh/authorized_keys /home/deploy/.ssh/authorized_keys && chown -R deploy:deploy /home/deploy/.ssh && chmod 700 /home/deploy/.ssh && chmod 600 /home/deploy/.ssh/authorized_keys"
```

- [ ] **Step 3: Verify `deploy` can log in via key**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "echo DEPLOY_LOGIN_OK"
```
Expected: prints `DEPLOY_LOGIN_OK`, no password prompt.

- [ ] **Step 4: Verify `deploy` can sudo**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo whoami"
```
Expected: prompts for `deploy`'s own password once (first sudo use may require setting one — if it fails with "no password set", run `ssh ... root@2.25.104.105 "passwd deploy"` first and set one interactively, then retry), then prints `root`.

**Do not proceed to Task 3 until both Step 3 and Step 4 pass.** This is the fail-safe checkpoint before root gets locked out.

### Task 3: Lock down SSH (disable root login and password auth)

**Files:** remote `/etc/ssh/sshd_config`

**Interfaces:**
- Consumes: verified `deploy` access from Task 2.
- Produces: SSH server that only accepts key-based `deploy` logins, no root, no passwords.

- [ ] **Step 1: Back up sshd_config before editing**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak"
```

- [ ] **Step 2: Disable root login and password auth**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/; s/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config"
```

- [ ] **Step 3: Validate the config syntax before restarting**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo sshd -t"
```
Expected: no output (silent success). If it errors, fix `/etc/ssh/sshd_config` before continuing — do not restart sshd with a broken config.

- [ ] **Step 4: Restart sshd**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo systemctl restart ssh"
```

- [ ] **Step 5: Verify root login is now rejected, in a NEW terminal session (keep the current one open in case of lockout)**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps root@2.25.104.105 "echo SHOULD_NOT_PRINT"
```
Expected: connection refused / "Permission denied (publickey)" — no output printed.

- [ ] **Step 6: Verify `deploy` login still works, in that same new session**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "echo STILL_WORKS"
```
Expected: prints `STILL_WORKS`. Only close the original session after this passes.

### Task 4: UFW firewall

**Files:** none (remote server state only)

**Interfaces:**
- Consumes: `deploy` SSH access from Task 3.
- Produces: firewall allowing only SSH/80/443, deny-by-default otherwise.

- [ ] **Step 1: Allow OpenSSH, HTTP, HTTPS**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo ufw allow OpenSSH && sudo ufw allow 80/tcp && sudo ufw allow 443/tcp"
```

- [ ] **Step 2: Set default deny for incoming, allow for outgoing**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo ufw default deny incoming && sudo ufw default allow outgoing"
```

- [ ] **Step 3: Enable UFW**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo ufw --force enable"
```

- [ ] **Step 4: Verify rules and that SSH still works**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo ufw status verbose"
```
Expected output includes `22/tcp (OpenSSH)  ALLOW  Anywhere`, `80/tcp  ALLOW  Anywhere`, `443/tcp  ALLOW  Anywhere`, default deny (incoming). The fact this SSH command itself succeeded is already proof SSH survived the firewall.

### Task 5: fail2ban

**Files:** remote `/etc/fail2ban/jail.local` (created)

**Interfaces:**

- Produces: running fail2ban service with the default `sshd` jail active.

- [ ] **Step 3: Restart and enable fail2ban on boot**

```bash
ssh -i ~/.ssh/id_ed25519_cozumel_vps deploy@2.25.104.105 "sudo systemctl restart fail2ban && sudo systemctl enable fail2ban"
```

- [ ] **Step 4: Verify the sshd jail is active**

```bash

```
Expected: output showing the `sshd` jail with `Status`, `Currently failed`, `Total failed`, `Currently banned` fields — no error.
